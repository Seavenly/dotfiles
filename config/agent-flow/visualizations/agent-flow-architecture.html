Agent Flow system map

Durable multi-agent execution without building a second scheduler

Agent Flow turns an approved software outcome into immutable contracts, versioned execution graphs, Hermes Kanban cards, validated evidence, and explicit review and delivery checkpoints. The system is local-first: implementation can be automated, but publication and completion remain deliberate.

What happens when a flow launches

A launch is preparation plus materialization. It never becomes a polling loop.

1. PrepareSkill creates approved durable inputs.
2. DoctorProfiles and runtime posture are fingerprinted.
3. SealRun manifest copies inputs and records digests.
4. ValidateTopology, paths, roots, caps, and revisions are checked.
5. MaterializeRoot starts blocked; all cards and links are created.
6. ExecuteHermes dispatches attempts and native retries.
7. FinalizeValidated evidence produces durable outputs and status.

How the system fails safely

Resilience is mostly durable visibility and bounded recovery, not invisible self-healing.

↻
Worker or gateway restart

Hermes retains cards, dependencies, attempts, and retry history. Resume uses the same run and IDs.

!
Semantic failure

The attempt completes with passed: false; a controller may create only a capped declared revision.

×
Malformed handoff

The validation card records why it failed and blocks every downstream consumer.

#
Changed sealed input

Resume derives the full compatibility delta and requires an exact append-only migration receipt.

⏸
Human decision needed

The same controller blocks with needs_input, naming the artifact and exact question.

∆
Branch or target drift

Approval becomes stale; verification, review, stack generation, and approval are repeated explicitly.

■
Cancellation race

Tenant-scoped sweeps reclaim and archive cards, while status reports any exact survivors.

≠
Partial Git delivery

Durable receipts reconcile completed mutations without repeating or pretending the operation finished.

A complete outcome, end to end

This is the longest path through the system: a multi-feature epic delivered through a reviewed stack.

  1. The epic skill seals intent.

    A feature dependency DAG, source branch, target SHA, limits, and tracker root become durable inputs.

  2. Hermes admits bounded ready waves.

    Independent features may execute concurrently, but every feature owns a separate worktree.

  3. Each feature runs serialized TDD slices.

    Tester, builder, deterministic gate, and controller chains repeat within one worktree until verification passes or a cap blocks.

  4. Completeness and independent critique close gaps.

    Only declared capped fix slices may re-enter implementation. RE_PLAN requires a human.

  5. A local review manifest freezes the candidate.

    The exact base and head SHAs, validation evidence, artifacts, and lifecycle generation become review truth.

  6. Reviewed features integrate into epic/source.

    Integration is serialized and receipt-backed. Any changed head invalidates review.

  7. Target drift is checked before stack planning.

    A moved target creates an explicit source-refresh graph, new verification, and a new stack generation.

  8. The stacks skill proposes exact review layers.

    Every hunk belongs to one layer; no branch or PR mutation happens before approval of the fixed plan.

  9. Each layer is reviewed and safe restacks preserve the prefix.

    Changes apply to the earliest owning layer. Only the unmerged suffix receives new generation refs.

  10. Delivery replays reviewed layers.

    epic/delivery must reproduce the exact source tree and pass full verification.

  11. One completion PR delivers the outcome.

    Only its verified merge can complete the external tracker issue.

Important design choices

These choices keep the system deep enough to be useful without turning it into a generic orchestration platform.

Why Hermes is the only control plane

Duplicating card state, retries, blocking, and recovery inside agent-flow would create two lifecycle authorities. The CLI prepares and audits; Hermes owns runtime state.

Why controller terminal access exists

Hermes v0.18.2 has no per-command plugin capability for repository transition helpers. Controllers receive terminal access contractually limited to the exact sealed agent-flow command on their card. This is narrow but not a filesystem sandbox.

Why worktrees are serialized

One feature has one worktree. Dependencies ensure only one tester, builder, retry, or fix slice writes at a time. Epic concurrency happens across independent feature worktrees, never within one feature worktree.

Why approval is bound to a SHA

A branch name can move. Review approval therefore names exactly one head SHA. Any head change, even a clean source merge, requires fresh verification and review.

Why stacks use deterministic replay

Replay makes each reviewed layer delta explicit, supports safe suffix restacking, preserves a reviewed prefix, and proves the final delivery tree equals the source tree without depending on commit identity.

Why Claude legacy flows still coexist

The local implementation and tests are complete, but live model-backed runs, real forge behavior, fresh UI inspection, and operational rollback evidence remain. The new agent-flow-* skill namespace allows both systems to coexist without naming collisions.

Current implementation posture

The repository implementation is complete through delivery; rollout confidence is intentionally tracked separately.

Implemented and locally verified

  • Profiles, doctoring, immutable run bundles, graph validation
  • Review, feature, spike, epic, stacks, and delivery operations
  • Handoff validation, deterministic gates, receipts, recovery
  • Local review lifecycle and tuicr projection
  • Exact hunk ownership, safe suffix restacks, exact-tree delivery

Rollout evidence still needed

  • Final model-backed sacrificial runs for every Hermes flow
  • Non-production remote stack and delivery prototype
  • Fresh dashboard and picker inspection on the final revision
  • Live backup and non-destructive prune rehearsal
